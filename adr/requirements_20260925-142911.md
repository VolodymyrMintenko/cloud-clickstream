# Requirements: DataSQRL Cloud web app clickstream

Date: 2026-09-25
Status: draft for planning

## Goal

Collect page views from the DataSQRL Cloud web application (`cloud-frontend`) and answer, over a
time window: which projects a given user returns to most often, which pages and tabs are used most,
which page-to-page transitions are common, and how many people use the product each day and week.

The consumer in this iteration is the DataSQRL team, reading this pipeline's GraphQL API through
GraphiQL. The pipeline itself runs as a project on DataSQRL Cloud, so the work is also a dogfooding
exercise for the platform and the DataSQRL coding agent.

## Scope

**In scope**

- One event type, `page_view`, ingested through a GraphQL mutation backed by Kafka.
- Sessionization of those events and page-to-page transition counting.
- The five queries listed under [API surface](#api-surface).
- Deployment as a DataSQRL Cloud project.

**Out of scope**

- Click-level or interaction tracking (button clicks, form input, scroll depth).
- Named product events such as "deployment created" or "project created". They are a natural next
  step and are deliberately excluded from this iteration.
- Traffic from self-hosted installations. Only the DataSQRL SaaS installation reports.
- Anonymous or logged-out traffic, and the marketing site.
- An admin dashboard in `cloud-frontend`. It is a separate task; iteration 1 is GraphiQL only.
- Session replay, funnels, retention cohorts beyond DAU/WAU, and alerting.
- Server-side API usage analytics (REST/GraphQL calls made by customers against their own
  deployments).

## Functional requirements

- **FR-1**: Accept `page_view` events through a GraphQL mutation; an accepted event is returned by
  the queries within 10 seconds of the mutation responding.
- **FR-2**: Require `event_id`, `session_id`, `user_id`, `org_id`, `org_name`, `route_pattern` and
  `path` on every event; an event missing any of them is rejected by the API and never enters the
  stream.
- **FR-3**: Deduplicate events on `event_id`, keeping the earliest arrival by event time.
- **FR-4**: Group events into sessions: events sharing a `session_id` belong to the same session
  while consecutive events are at most 30 minutes apart; a larger gap starts a new session.
- **FR-5**: Assign every event its position in the session (1-based) and its dwell time, defined as
  the event time of the next event in the session minus its own; the last event of a session has a
  null dwell time.
- **FR-6**: Expose `TopProjectsByUser(userId, fromTime, toTime, limit)` returning `projectId`,
  `orgName`, `viewCount`, `sessionCount` and `lastViewedAt`, ordered by `viewCount` descending.
- **FR-7**: Expose `TopPages(fromTime, toTime, limit, includeAdmins)` returning `routePattern`,
  `viewCount`, `uniqueUsers` and `uniqueSessions`, ordered by `viewCount` descending.
- **FR-8**: Expose `PageTransitions(fromRoutePattern, fromTime, toTime, limit)` returning
  `toRoutePattern` and `transitionCount`, ordered by `transitionCount` descending, counting only
  consecutive events inside one session.
- **FR-9**: Expose `SessionJourney(sessionId)` returning the session's events ordered by event time,
  each with `sequence`, `routePattern`, `path`, `projectId`, `deploymentId`, `tab`, `eventTime` and
  `dwellSeconds`.
- **FR-10**: Expose `ActiveUsers(fromTime, toTime)` returning, per day, the number of distinct
  users (DAU) and the number of distinct users over the trailing 7 days (WAU).
- **FR-11**: Carry `isGlobalAdmin` on every event and let the page and project queries exclude
  events where it is true, so DataSQRL staff browsing customer projects does not distort the
  numbers.

## Sources

### `PageView`

- **Transport**: GraphQL mutation `PageView(event: PageViewInput!)`, backed by a Kafka-engine table
  in the style of `code-agent/sqrl_templates/content_recommendation/connectors/clickstream.sqrl`.
  It is served by a DataSQRL Cloud project of our own. The only producer is `cloud-frontend`'s
  internal Next.js route `POST /api/v1/events/page-view`, which the browser calls on first load and
  after every client-side navigation. The browser never calls the pipeline directly, and the route
  supplies `user_id`, `org_id`, `org_name` and `is_global_admin` from the server-side session, so
  those four fields cannot be forged by a client.
- **Format**: JSON.
- **Sample payload** (one mutation input; ids are opaque strings produced by cloud-backend and
  Auth0, shown redacted):

```json
{
  "event_id": "b3f1c4f2-6f0a-4c3f-9b6e-1d2a6b0f3c11",
  "session_id": "5f2a9c7e-3b41-4f9a-9a3d-0c8e5b7d2a10",
  "user_id": "auth0|000000000000000000000000",
  "is_global_admin": false,
  "org_id": "0f6f2f3a-0000-0000-0000-2b7c1d9e4a55",
  "org_name": "acme",
  "route_pattern": "/[orgName]/[projectId]/[deploymentId]/~/logs",
  "path": "/acme/2f9d1c44-0000-0000-0000-8a1b6c3d7e20/7c4e0b91-0000-0000-0000-15d2f8a6b039/~/logs",
  "project_id": "2f9d1c44-0000-0000-0000-8a1b6c3d7e20",
  "deployment_id": "7c4e0b91-0000-0000-0000-15d2f8a6b039",
  "tab": "logs",
  "referrer_path": "/acme/2f9d1c44-0000-0000-0000-8a1b6c3d7e20/~/deployments"
}
```

| Field | Type | Nullable | Meaning |
|---|---|---|---|
| `event_id` | STRING | no | UUID v4 generated per page view in the browser; the deduplication key |
| `session_id` | STRING | no | UUID v4 held in `sessionStorage`; a new tab starts a new id |
| `user_id` | STRING | no | Auth0 subject id, set server-side; never an email |
| `is_global_admin` | BOOLEAN | no | set server-side; true for DataSQRL staff accounts |
| `org_id` | STRING | no | active organization id, set server-side |
| `org_name` | STRING | no | organization slug as it appears in the URL |
| `route_pattern` | STRING | no | Next.js route pattern, the grouping key for "which page" |
| `path` | STRING | no | resolved path, without query string or fragment |
| `project_id` | STRING | yes | null outside a project route |
| `deployment_id` | STRING | yes | null outside a deployment route |
| `tab` | STRING | yes | segment after `~`; null on pages that have no tabs |
| `referrer_path` | STRING | yes | previous in-app path; null on the first view of a session |
| `event_time` | TIMESTAMP_LTZ(3) | no | Kafka metadata timestamp; not client-supplied |

- **Route patterns** (the complete surface, 42 pages; `~` is a literal separator segment in this
  application, not a wildcard):

```
/
/[orgName]
/[orgName]/~                       /[orgName]/~/{alerts,assistant,governance,people,settings,utilization}
/[orgName]/[projectId]
/[orgName]/[projectId]/~           /[orgName]/[projectId]/~/{alerts,analytics,assistant,deployments,logs,settings,utilization}
/[orgName]/[projectId]/[deploymentId]
/[orgName]/[projectId]/[deploymentId]/~
/[orgName]/[projectId]/[deploymentId]/~/{alerts,analytics,api,assistant,config,data-flow,data-model,logs,source}
/~/governance
/docs  /profile  /release-notes  /upgrade-notes  /utilization
/auth/error  /auth/unavailable
/admin  /admin/installations  /admin/orgs  /admin/users
```

- **Volume and rate**: low. Assume 5,000 events/day on average, under 1 event/second sustained,
  50 events/second peak. Growth tracks product adoption, not traffic spikes. See Decisions.
- **Delivery guarantee**: at-least-once. The browser may retry a failed send, so the same
  `event_id` can arrive more than once. There is no replay source; a lost event is lost.
- **Duplicates and ordering**: a duplicate is a repeated `event_id`; the earliest arrival wins.
  Per-session ordering is established by sorting on `event_time` in SQL, not by Kafka partition
  order.
- **Updates**: events are immutable. No CDC, no upserts, no deletes.

## Time semantics

- **Event-time field**: `event_time`, taken from the Kafka record metadata
  (`METADATA FROM 'timestamp'`), in UTC. No client clock is trusted, because browser clocks are
  unreliable and a skewed one would corrupt sessionization.
- **Lateness**: the frontend route calls the mutation synchronously while handling the browser
  request, so the metadata timestamp is within about a second of the actual view. Tolerate 60
  seconds of lateness; treat anything beyond that as impossible.
- **Processing time acceptable?**: `event_time` as defined above *is* ingest time. This is a
  deliberate choice, not a fallback: it is accurate to within a second and immune to client clock
  skew.

## Entities and keys

| Entity | Key | Notes |
|---|---|---|
| `PageView` | `event_id` | the raw immutable event |
| `Session` | `session_id` | belongs to exactly one `user_id`; bounded by the 30-minute gap rule |
| `User` | `user_id` | opaque Auth0 subject; no profile data is carried in this pipeline |
| `Organization` | `org_id` | `org_name` is the URL slug and may change; `org_id` is the stable key |
| `Project` | `project_id` | unique within an organization; appears only as a dimension of events |
| `Deployment` | `deployment_id` | belongs to a project; a dimension only |

No shared data catalog exists for this pipeline. Users, organizations, projects and deployments
live in cloud-backend and are **not** joined here; only their ids and the organization slug travel
with the event. A query returns ids, and the reader resolves names elsewhere.

## Transformations and aggregations

1. **Deduplicated events** — input: raw `PageView`; key: `event_id`; unbounded; keep the earliest
   by `event_time`. Everything downstream reads this, not the raw stream. *(FR-3)*
2. **Sessionized events** — input: deduplicated events; partition by `session_id`, order by
   `event_time`; a gap over 30 minutes to the previous event opens a new session (the session
   identity becomes `session_id` plus the ordinal of the gap-separated run). Emits `sequence` and
   the previous event's `route_pattern`. Nothing here references a later event; `dwell_seconds` is
   derived at query time by `SessionJourney`. *(FR-4, FR-5)*
3. **Project views per user, daily** — input: sessionized events with a non-null `project_id`;
   group by `user_id`, `project_id`, `org_name`, day; aggregate `view_count`,
   `distinct session_count`, `max(event_time)`. A window query sums over days. *(FR-6)*
4. **Page views, daily** — group by `route_pattern`, `is_global_admin`, day; aggregate
   `view_count`, `distinct users`, `distinct sessions`. Keeping `is_global_admin` in the grouping
   key is what lets FR-7 include or exclude staff without a second pipeline. *(FR-7, FR-11)*
5. **Transitions, daily** — from sessionized events, pair each event with the previous one in the
   same session; group by `from_route_pattern`, `to_route_pattern`, day; count. The first event of a
   session produces no pair. *(FR-8)*
6. **Active users, daily** — group by day, count distinct `user_id`; WAU is the distinct count over
   the trailing 7 days, which is not a sum of daily values and must be computed as its own sliding
   aggregate. *(FR-10)*

Late data: an event arriving inside the 60-second tolerance updates the daily bucket of its own
`event_time`; the aggregates are incremental, so a previously emitted bucket is corrected rather
than duplicated.

## API surface

**Mutations**

- `PageView(event: PageViewInput!)` — the single write path, fields exactly as the source table
  above. Returns the accepted event so the caller can confirm receipt. *(FR-1, FR-2)*

**Queries** — the questions the team actually asks:

| Query | Parameters | Returns |
|---|---|---|
| `TopProjectsByUser` | `userId`, `fromTime`, `toTime`, `limit` | `projectId`, `orgName`, `viewCount`, `sessionCount`, `lastViewedAt` |
| `TopPages` | `fromTime`, `toTime`, `limit`, `includeAdmins` | `routePattern`, `viewCount`, `uniqueUsers`, `uniqueSessions` |
| `PageTransitions` | `fromRoutePattern`, `fromTime`, `toTime`, `limit` | `toRoutePattern`, `transitionCount` |
| `SessionJourney` | `sessionId` | ordered events: `sequence`, `routePattern`, `path`, `projectId`, `deploymentId`, `tab`, `eventTime`, `dwellSeconds` |
| `ActiveUsers` | `fromTime`, `toTime` | per day: `day`, `dau`, `wau` |

**Subscriptions**: none.

**Access**: the caller's Auth0 token. `cloud-frontend` already attaches
`Authorization: Bearer <user.accessToken>` to every call it makes to the Agent and Metrics APIs
(`apollo-client-builder.service.ts`), and the DataSQRL API engine validates it through
`"authKind": ["JWT"]` with the issuer and audience given in the package configuration, the way
`sqrl_templates/user_analytics` does. No new shared secret is introduced. Team members reading the
queries authenticate with their own token. Independently of that, the payload carries no personal
data beyond opaque ids (see NFR-4).

There is no tenant field in the access sense: every row belongs to DataSQRL itself, and `org_id` is
a reporting dimension, not an isolation boundary.

## Test data and acceptance criteria

**Test data** — roughly 20 events covering 2 organizations, 3 users (one with
`is_global_admin = true`), 4 projects, and these edge cases: a repeated `event_id`; two events
arriving out of order; an event with null `project_id`, `deployment_id` and `tab` (for example
`/profile`); a null `referrer_path` at the start of a session; a 45-minute gap inside one
`session_id`; a session holding exactly one event; two users viewing the same project.

**Acceptance criteria**

- *(FR-1)* After `PageView` returns for a fresh event, `TopPages` over a window containing it
  includes its `route_pattern` within 10 seconds.
- *(FR-2)* A mutation missing `session_id` fails and no row appears in any query.
- *(FR-3)* Given 20 events of which one `event_id` appears twice, the totals across `TopPages`
  count it once.
- *(FR-4)* Given one `session_id` whose events straddle a 45-minute gap, `ActiveUsers` is
  unaffected while the transition across the gap is **not** counted by `PageTransitions`, because
  the gap ends the session.
- *(FR-5)* For a session of 3 events at t, t+30s, t+90s, `SessionJourney` returns
  `dwellSeconds` of 30, 60 and null, with `sequence` 1, 2, 3.
- *(FR-6)* For a user with 5 views of project A and 2 of project B, `TopProjectsByUser` returns A
  first with `viewCount` 5 and `lastViewedAt` equal to the latest of those 5 event times.
- *(FR-7)* `TopPages` with `includeAdmins: false` returns counts that exclude every event of the
  admin user, and with `includeAdmins: true` returns the full counts.
- *(FR-8)* Given the session `/[orgName]/[projectId]/~/deployments` then
  `/[orgName]/[projectId]/[deploymentId]/~/logs`, `PageTransitions` for the first pattern returns
  the second with `transitionCount` 1.
- *(FR-9)* `SessionJourney` for a single-event session returns exactly one row with `sequence` 1
  and null `dwellSeconds`.
- *(FR-10)* With 3 distinct users active on one day and 1 of them also active 3 days earlier,
  that day's `dau` is 3 and its `wau` is 3.
- *(FR-11)* Every stored event exposes `isGlobalAdmin`, and the fixture's admin events are
  reachable when `includeAdmins` is true.

## Non-functional requirements

- **NFR-1 Freshness**: 10 seconds at p95, measured from the mutation response to the event being
  returned by `TopPages`.
- **NFR-2 Throughput**: sustain 5 events/second; absorb 50 events/second for 5 minutes without
  rejecting events.
- **NFR-3 Retention**: 30 days, for raw events and every aggregate alike. Past that boundary data is
  dropped, so no query answers beyond the last 30 days. Because raw events are kept for the whole
  query horizon, window aggregates are computed from them exactly rather than approximated from
  daily buckets.
- **NFR-4 PII and sensitive fields**: the payload carries no email, display name, IP address, user
  agent, query string, fragment or free text. `user_id` and `org_id` are opaque ids that resolve to
  a person only inside cloud-backend. `path` contains the organization slug and resource ids, which
  are already present as their own columns and are not secret. This holds regardless of the JWT on
  the API: the data is uninteresting to an attacker even if a token leaks.
- **NFR-5 Availability**: ingest failure is invisible to the web application. `cloud-frontend`
  sends events without blocking a render and ignores the result; an outage of this pipeline loses
  events for its duration and that loss is acceptable.
- **NFR-6 Deployment**: the deliverable is a deployable DataSQRL Cloud project, so the run produces
  the project files including a `-prod` package overlay. Creating the project on the platform and
  deploying it is done separately and is not part of this run.

## Decisions

Settled with the product owner on 2026-09-25. They are listed so that planning does not reopen them.

- **Where it runs**: a DataSQRL Cloud project of our own; nobody has to provision infrastructure
  for it. Running the pipeline in a container the team operates by hand was rejected: it would make
  us the operators of a Flink cluster for internal statistics.
- **Event volume**: 5,000 events/day on average, 50 events/second peak, accepted as an estimate and
  not a measurement. NFR-2 sits roughly 86x above that estimate, so a wrong guess costs nothing.
- **Kafka partition key**: the pipeline does not depend on partition ordering. Per-session order
  comes from sorting on `event_time` in SQL, whether or not the connector can key records by
  `session_id`.
- **Deletion of one user's events on request (GDPR)**: not built. Events disappear with the 30-day
  retention in NFR-3. Should targeted deletion ever be required, storage has to be reworked.
- **Staff traffic**: stored, flagged with `is_global_admin`, and excluded by default, so
  `includeAdmins` defaults to false in `TopPages`.
- **Session definition**: the `sessionStorage` id plus a 30-minute inactivity cut, so a tab left
  open overnight does not become one 12-hour session.
- **Bot and prefetch filtering**: none. Next.js prefetching does not run the client navigation hook,
  and unauthenticated requests never reach the ingest route, so neither produces events. If junk
  does appear in the data, a user-agent filter is added at that point.

## Open Questions

None. The decisions above were settled on 2026-09-25, and where the pipeline is deployed is DevOps'
to decide: the frontend consumes whatever endpoint they hand back.
