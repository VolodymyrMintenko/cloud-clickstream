## Requirements Summary

Build a low-volume (≈5,000 events/day) internal analytics pipeline that ingests `page_view` events
from the DataSQRL Cloud frontend through a single GraphQL **mutation** backed by a Kafka-engine
table, deduplicates them on `event_id`, sessionizes them under a 30-minute inactivity rule, and
serves five GraphQL query functions over time windows (top projects per user, top pages,
page-to-page transitions, a single session's journey, and DAU/WAU). Event time is the Kafka
metadata timestamp (ingest time), not a client clock. Engines: Flink (processing), Kafka (mutation
ingestion), Postgres (served queries), Vert.x (GraphQL/REST/MCP API with JWT auth). Retention is
enforced with per-table `ttl` (30 days on every table, raw and aggregate alike). The full source specification is `adr/requirements_20260925-142911.md`; the
load-bearing material is copied into the reference sections below.

## Requirements Reference

Full text of every requirement cited in this plan (source: `adr/requirements_20260925-142911.md`,
lines 41–309):

- **FR-1** — Accept `page_view` events through a GraphQL mutation; an accepted event is returned by
  the queries within 10 seconds of the mutation responding.
- **FR-2** — Require `event_id`, `session_id`, `user_id`, `org_id`, `org_name`, `route_pattern` and
  `path` on every event; an event missing any of them is rejected by the API and never enters the
  stream.
- **FR-3** — Deduplicate events on `event_id`, keeping the earliest arrival by event time.
- **FR-4** — Group events into sessions: events sharing a `session_id` belong to the same session
  while consecutive events are at most 30 minutes apart; a larger gap starts a new session.
- **FR-5** — Assign every event its position in the session (1-based) and its dwell time, defined
  as the event time of the next event in the session minus its own; the last event of a session
  has a null dwell time.
- **FR-6** — Expose `TopProjectsByUser(userId, fromTime, toTime, limit)` returning `projectId`,
  `orgName`, `viewCount`, `sessionCount` and `lastViewedAt`, ordered by `viewCount` descending.
- **FR-7** — Expose `TopPages(fromTime, toTime, limit, includeAdmins)` returning `routePattern`,
  `viewCount`, `uniqueUsers` and `uniqueSessions`, ordered by `viewCount` descending.
- **FR-8** — Expose `PageTransitions(fromRoutePattern, fromTime, toTime, limit)` returning
  `toRoutePattern` and `transitionCount`, ordered by `transitionCount` descending, counting only
  consecutive events inside one session.
- **FR-9** — Expose `SessionJourney(sessionId)` returning the session's events ordered by event
  time, each with `sequence`, `routePattern`, `path`, `projectId`, `deploymentId`, `tab`,
  `eventTime` and `dwellSeconds`.
- **FR-10** — Expose `ActiveUsers(fromTime, toTime)` returning, per day, the number of distinct
  users (DAU) and the number of distinct users over the trailing 7 days (WAU).
- **FR-11** — Carry `isGlobalAdmin` on every event and let the page and project queries exclude
  events where it is true, so DataSQRL staff browsing customer projects does not distort the
  numbers.
- **NFR-1 Freshness** — 10 seconds at p95, measured from the mutation response to the event being
  returned by `TopPages`.
- **NFR-2 Throughput** — sustain 5 events/second; absorb 50 events/second for 5 minutes without
  rejecting events.
- **NFR-3 Retention** — 30 days, for raw events and every aggregate alike. Past that boundary data
  is dropped, so no query answers beyond the last 30 days. Because raw events are kept for the whole
  query horizon, window aggregates are computed from them exactly rather than approximated from
  daily buckets.
- **NFR-4 PII** — payload carries no email, name, IP, user agent, query string, fragment or free
  text; `user_id`/`org_id` are opaque ids. No masking or claims-based row filtering is required.
- **NFR-5 Availability** — ingest failure is invisible to the web app; a lost event during an
  outage is acceptable.
- **NFR-6 Deployment** — the deliverable is a deployable DataSQRL Cloud project, so the run
  produces the project files including a `-prod` package overlay. Creating the project on the
  platform and deploying it is done separately and is not part of this run.
- **Time semantics** (lines 147–157) — event time is `event_time`, taken from the Kafka record
  metadata (`METADATA FROM 'timestamp'`), in UTC; no client clock is trusted. Tolerate 60 seconds
  of lateness. `event_time` as defined *is* ingest time, by deliberate choice.
- **D-partition-key** (line 297) — the pipeline does not depend on Kafka partition ordering;
  per-session order comes from sorting on `event_time` in SQL.
- **D-staff** (line 302) — staff traffic is stored, flagged with `is_global_admin`, and excluded by
  default, so `includeAdmins` defaults to false in `TopPages`.
- **D-session** (line 304) — session = the `sessionStorage` id plus a 30-minute inactivity cut.

## Source Payloads & Schemas

Single source, **`PageView`** (source of truth: `adr/requirements_20260925-142911.md`, lines
72–145).

- **Transport (production)**: GraphQL mutation `PageView(event: PageViewInput!)`, backed by a
  Kafka-engine table (`/*+no_query, engine(kafka) */`), in the style of
  `/opt/sqrl_templates/content_recommendation/connectors/clickstream.sqrl`. The only producer is
  `cloud-frontend`'s internal Next.js route `POST /api/v1/events/page-view`. `user_id`, `org_id`,
  `org_name` and `is_global_admin` are set server-side and cannot be forged by a client.
- **Transport (test)**: a filesystem connector over a static JSONL file with `event_time` as a
  physical column carrying deterministic values — the standard "test connectors mirror production"
  substitution (`/manage-connector`). Ingest-time metadata is not deterministic, so sessionization,
  dwell and day-bucket tests require controlled `event_time`.
- **Format**: JSON.
- **Sample payload** (one mutation input, verbatim; ids redacted opaque strings):

```json
{
  "event_id": "b3f1c4f2-6f0a-4c3f-9b6e-1d2a6b0f3c11",
  "session_id": "5f2a9c7e-3b41-4f9a-9a3d-0c8e5b7d2a10",
  "user_id": "auth0|000000000000000000000000",
  "is_global_admin": false,
  "org_id": "0f6f2f3a-0000-0000-0000-2b7c1d9e4a55",
  "org_name": "acme",
  "route_pattern": "/[orgName]/[projectId]/[deploymentId]/~/logs",
  "path": "/acme/2f9d1c44-0000-0000-0000-8a1b6c3d7e20/7c4e0b91-0000-0000-0000-15d2f8a6b039/~/logs",
  "project_id": "2f9d1c44-0000-0000-0000-8a1b6c3d7e20",
  "deployment_id": "7c4e0b91-0000-0000-0000-15d2f8a6b039",
  "tab": "logs",
  "referrer_path": "/acme/2f9d1c44-0000-0000-0000-8a1b6c3d7e20/~/deployments"
}
```

- **Field table** (verbatim):

| Field | Type | Nullable | Meaning |
|---|---|---|---|
| `event_id` | STRING | no | UUID v4 per page view; the deduplication key |
| `session_id` | STRING | no | UUID v4 in `sessionStorage`; a new tab starts a new id |
| `user_id` | STRING | no | Auth0 subject id, set server-side; never an email |
| `is_global_admin` | BOOLEAN | no | set server-side; true for DataSQRL staff accounts |
| `org_id` | STRING | no | active organization id, set server-side |
| `org_name` | STRING | no | organization slug as it appears in the URL |
| `route_pattern` | STRING | no | Next.js route pattern, the grouping key for "which page" |
| `path` | STRING | no | resolved path, without query string or fragment |
| `project_id` | STRING | yes | null outside a project route |
| `deployment_id` | STRING | yes | null outside a deployment route |
| `tab` | STRING | yes | segment after `~`; null on pages that have no tabs |
| `referrer_path` | STRING | yes | previous in-app path; null on the first view of a session |
| `event_time` | TIMESTAMP_LTZ(3) | no | Kafka metadata timestamp; not client-supplied |

- **Column ownership**: `event_time` is NOT a payload column — it is the Kafka metadata timestamp
  in production and a physical file column in test. All twelve payload columns above (through
  `referrer_path`) belong in the shared `_PageView_schema`; `event_time` and the `WATERMARK` belong
  in each per-environment connector table. There are no nested/array types — the payload is flat.
- **Route patterns** (the complete surface, 42 pages; `~` is a literal separator segment, not a
  wildcard; source lines 116–133):

```
/
/[orgName]
/[orgName]/~                       /[orgName]/~/{alerts,assistant,governance,people,settings,utilization}
/[orgName]/[projectId]
/[orgName]/[projectId]/~           /[orgName]/[projectId]/~/{alerts,analytics,assistant,deployments,logs,settings,utilization}
/[orgName]/[projectId]/[deploymentId]
/[orgName]/[projectId]/[deploymentId]/~
/[orgName]/[projectId]/[deploymentId]/~/{alerts,analytics,api,assistant,config,data-flow,data-model,logs,source}
/~/governance
/docs  /profile  /release-notes  /upgrade-notes  /utilization
/auth/error  /auth/unavailable
/admin  /admin/installations  /admin/orgs  /admin/users
```

- **Delivery semantics**: at-least-once. A repeated `event_id` is a duplicate; the earliest arrival
  by `event_time` wins (FR-3). No replay source; a lost event is lost. Per-session ordering comes
  from sorting on `event_time` in SQL, not partition order (D-partition-key). Events are immutable
  — no CDC, upserts, or deletes. Lateness tolerance 60 seconds.
- **Volume**: ≈5,000 events/day average, <1 event/s sustained, 50 events/s peak (NFR-2).

## API Contract

The requirements fix the API surface (source lines 199–227). It is not given as a schema file, so
the SQRL query functions must be shaped to produce these exact operation names, argument names, and
result field names (camelCase). The API is derived forward from SQRL (`/design-api`); where the
generated names would not match, columns are aliased to the contract names, or an explicit
`schema.v1.graphqls` is written (`/from-api`). No operation may be silently widened or renamed.

**Mutation**
- `PageView(event: PageViewInput!)` — the single write path. `PageViewInput` fields are exactly the
  twelve payload fields above (all except `event_time`, which is metadata). Returns the accepted
  event including `event_time` so the caller can confirm receipt (FR-1). Required-non-null on
  `event_id`, `session_id`, `user_id`, `is_global_admin`, `org_id`, `org_name`, `route_pattern`,
  `path`; nullable on `project_id`, `deployment_id`, `tab`, `referrer_path` (FR-2).

**Queries**

| Query | Parameters | Returns |
|---|---|---|
| `TopProjectsByUser` | `userId`, `fromTime`, `toTime`, `limit` | `projectId`, `orgName`, `viewCount`, `sessionCount`, `lastViewedAt` |
| `TopPages` | `fromTime`, `toTime`, `limit`, `includeAdmins` | `routePattern`, `viewCount`, `uniqueUsers`, `uniqueSessions` |
| `PageTransitions` | `fromRoutePattern`, `fromTime`, `toTime`, `limit` | `toRoutePattern`, `transitionCount` |
| `SessionJourney` | `sessionId` | ordered events: `sequence`, `routePattern`, `path`, `projectId`, `deploymentId`, `tab`, `eventTime`, `dwellSeconds` |
| `ActiveUsers` | `fromTime`, `toTime` | per day: `day`, `dau`, `wau` |

- Ordering: `TopProjectsByUser` by `viewCount` desc; `TopPages` by `viewCount` desc;
  `PageTransitions` by `transitionCount` desc; `SessionJourney` by event time asc; `ActiveUsers`
  by day.
- **Subscriptions**: none — so no `SUBSCRIBE` and no dependence on Kafka for subscription delivery
  (Kafka is enabled only for the mutation write path).
- **Access**: JWT authentication at the API engine (`vertx` `"authKind": ["JWT"]`), issuer/audience
  in package config, exactly as `user_analytics`. JWT is **authentication only** — there is no
  claims-based row filtering or tenant isolation (`org_id` is a reporting dimension, not a boundary;
  NFR-4). No `METADATA FROM 'auth.*'` argument injection is required.

## Scenario Analysis

**Axis 1 — artifact type: `pipeline`.** The deliverable ingests from a source, processes/aggregates,
and exposes a GraphQL/REST/MCP API from `.sqrl` scripts plus `*-package.json` files.

**Axis 2 — task type: `new-project`.** No `.sqrl` files exist; the pipeline is built from scratch
starting from the `event_processing` template.

**Stateful-operation / state-growth analysis** (drives the retention and windowing decisions):
- **Deduplication** (`DISTINCT ... ON event_id`) is unbounded state keyed by `event_id`; bounded by
  a 30-day `ttl` (NFR-3).
- **Daily aggregates** grouped on a computed UTC `day` bucket are continuously-updating (mutable)
  state keyed by (dimensions, day); each event corrects its day's bucket in place — "incremental,
  corrected rather than duplicated" (source lines 194–197). Plain day-bucket GROUP BY updates the
  served row on every event → sub-second propagation, meeting NFR-1's 10 s freshness. State bounded
  by `ttl` (30 days per NFR-3).
- **WAU** is a 7-day trailing distinct count — not a sum of daily values — so it is computed as its
  own sliding (HOP) aggregate, 1-day slide over a 7-day window, keyed by day.
- **Sessionization** (30-minute gap split) and **transitions** need row-adjacency within a session,
  which is the one genuinely order-sensitive computation (see Technical Decisions).

## Acceptance Criteria

Copied verbatim from `adr/requirements_20260925-142911.md` lines 237–261; expected values are the
test oracle and must not be recomputed or rounded:

- *(FR-1)* After `PageView` returns for a fresh event, `TopPages` over a window containing it
  includes its `route_pattern` within 10 seconds.
- *(FR-2)* A mutation missing `session_id` fails and no row appears in any query.
- *(FR-3)* Given 20 events of which one `event_id` appears twice, the totals across `TopPages`
  count it once.
- *(FR-4)* Given one `session_id` whose events straddle a 45-minute gap, `ActiveUsers` is
  unaffected while the transition across the gap is **not** counted by `PageTransitions`, because
  the gap ends the session.
- *(FR-5)* For a session of 3 events at t, t+30s, t+90s, `SessionJourney` returns `dwellSeconds` of
  30, 60 and null, with `sequence` 1, 2, 3.
- *(FR-6)* For a user with 5 views of project A and 2 of project B, `TopProjectsByUser` returns A
  first with `viewCount` 5 and `lastViewedAt` equal to the latest of those 5 event times.
- *(FR-7)* `TopPages` with `includeAdmins: false` returns counts that exclude every event of the

- *(FR-8)* Given the session `/[orgName]/[projectId]/~/deployments` then
  `/[orgName]/[projectId]/[deploymentId]/~/logs`, `PageTransitions` for the first pattern returns
  the second with `transitionCount` 1.
- *(FR-9)* `SessionJourney` for a single-event session returns exactly one row with `sequence` 1
  and null `dwellSeconds`.
- *(FR-10)* With 3 distinct users active on one day and 1 of them also active 3 days earlier, that

## Technical Decisions

- **Ingestion = Kafka-engine GraphQL mutation, event time from metadata.** `PageView` is a
  `/*+no_query, engine(kafka) */` table (content_recommendation clickstream pattern) so the write
  path is a GraphQL mutation and Kafka absorbs the 50 events/s peak (NFR-2). `event_time` is
  `METADATA FROM 'timestamp'` (ingest time), not a client field, because browser clocks are
  untrusted (Time semantics) — this is also why `event_time` is excluded from `PageViewInput`.
- **Environment-specific source, test mirrors production.** The main script imports
  `pageview-{{environment}}`; prod/local define the Kafka mutation (metadata `event_time`), test
  defines a filesystem table of the same name with `event_time` as a physical column carrying static
  values. This is the only way to make sessionization, dwell, and day-bucket tests deterministic —
  ingest-time metadata is wall-clock. Consequence: FR-1/FR-2 (write path) are verified against the
  Kafka-backed local environment (receipt and rejection, not event-time-dependent); FR-3–FR-11
  logic is verified against the deterministic filesystem test environment.
- **Engine set `flink, postgres, kafka, vertx` — no iceberg/duckdb.** Kafka is required only for the
  mutation; there is no data-lake export and no subscription. The 30-day retention is met by
  Postgres state with `ttl`, not by an Iceberg archive, keeping the engine set minimal.
- **Deduplication keeps the earliest arrival.** `DISTINCT ON event_id` ordered ascending by
  `event_time` — a re-delivered `event_id` cannot displace the first (FR-3). Bounded by 30-day
  `ttl`.
- **Daily aggregates use a computed UTC `day` bucket with continuously-updating GROUP BY, not a
  TUMBLE/CUMULATE window.** A plain group-by-day aggregate corrects the current day's bucket in place
  on each event (the requirements' "incremental, corrected rather than duplicated" model) and
  propagates within sub-seconds, meeting NFR-1's 10 s freshness — a CUMULATE step (≥1 min) or TUMBLE
  (hour/day close) would not. Day bucketing is UTC.
- **WAU is a sliding (HOP) 7-day distinct count, computed separately from DAU and joined by day.**
  WAU is not the sum of daily DAU (source line 191), so it is its own 1-day-slide / 7-day-size HOP
  aggregate. DAU is the day-bucket distinct count. Freshness of WAU is not constrained by NFR-1
  (which names `TopPages`).
- **Sessionization looks backward only; `dwell_seconds` is computed at serve time.** Nothing in the
  stream references a later event. Within each `session_id`, order by `event_time` and compare each
  event to the **prior** one: a gap > 30 min starts a new session run, the running count of gap
  boundaries yields the session-run ordinal, and `ROW_NUMBER` yields the 1-based `sequence`. A page
  transition is the pair (prior event's `route_pattern`, this event's `route_pattern`) within the
  same run, so the **first** event of a run produces no pair; every adjacent pair is still counted
  exactly once, identically to a forward pairing (FR-8). `dwell_seconds` is the one genuinely
  forward-looking value, so it is not computed in the stream at all: `SessionJourney` derives it in
  Postgres with `LEAD` over the session's rows at query time, leaving null on the last event
  (FR-5, FR-9). This removes the unsupported-construct risk rather than keeping it as a fallback.
- **Window uniques are exact.** `TopPages.uniqueUsers`/`uniqueSessions` and
  `TopProjectsByUser.sessionCount` are counted distinct over the retained raw events inside the
  query window, not summed from per-day distinct counts, so a user active on several days counts
  once. Raw retention covers the whole 30-day query horizon (NFR-3) and the volume is small enough
  (about 150,000 rows) that the exact count is cheap.
- **API names shaped to the contract.** Query functions and result columns are named/aliased to the
  exact camelCase operation, argument, and field names in `## API Contract`; an explicit
  `web_clickstream-api/schema.v1.graphqls` is written only if the inferred schema cannot match.
- **JWT is authentication only.** `vertx` `"authKind": ["JWT"]` with issuer/audience validation
  (user_analytics pattern); no claims are mapped to arguments and no row-level filtering — every row
  belongs to DataSQRL and `org_id` is a reporting dimension, not an isolation boundary (NFR-4).

## Assumptions

- **Sessionization mechanics**: Assumed the 30-minute gap-split, per-event `sequence` and the
  previous-event `from_route_pattern` can be computed with backward-looking streaming OVER-window
  functions over the deduplicated stream, and that `dwell_seconds` is derived at query time in
  Postgres. Rationale: backward-looking window functions over a stream are ordinary; moving the one
  forward-looking value to the served query removes the unverified construct entirely.
  [impact: medium]
- **Test source substitution**: Assumed the production Kafka mutation is replaced by a filesystem
  connector of the same table name in the test environment (with a physical static `event_time`),
  and that write-path FR-1/FR-2 are validated in a Kafka-backed local environment. Rationale: this
  is the standard "test connectors mirror production" pattern and the only way to get deterministic
  sessionization snapshots. [impact: high]
- **Engine set**: Assumed `flink, postgres, kafka, vertx` with no Iceberg/DuckDB; 30-day retention
  via Postgres `ttl`. Rationale: no data-lake export or subscription is required, so extra engines
  add only deployment cost. [impact: high]
- **`ttl` satisfies retention semantics**: Assumed per-table `ttl` (30 days) both bounds
  operator state and enforces NFR-3's answerable-history boundaries. Rationale: `ttl` is the
  documented DataSQRL retention control; the requirements describe exactly a per-table retention
  boundary. [impact: medium]
- **Window uniques exact**: Assumed `uniqueUsers`/`uniqueSessions`/`sessionCount` are counted
  distinct over the retained raw events in the query window, so a user active on several days counts
  once. Rationale: raw retention covers the whole 30-day query horizon and about 150,000 rows make
  the exact count cheap. [impact: medium]
- **Day bucket = UTC calendar day**: Assumed `day` is the UTC-truncated `event_time`, and `fromTime`/
  `toTime` query bounds are half-open `[from, to)`. Rationale: all payload timestamps are UTC (Time
  semantics); half-open bounds avoid double-counting boundary days. [impact: medium]
- **JWT algorithm and keys**: Assumed HS256 with dummy issuer/audience/secret in test and local
  (mirroring `user_analytics`), with the real issuer/audience filled in from the platform's Auth0
  configuration when the prod project is deployed. Rationale: the requirements name user_analytics
  as the model and leave the concrete issuer to deployment time. [impact: medium]
- **Kafka topic / DATA_PATH naming**: Assumed logical hardcoded names for the mutation topic and the
  test `${DATA_PATH}/page_view.jsonl`, with only per-deployment values as `${VARIABLES}`. Rationale:
  topic names are identical across deployments and not sensitive. [impact: low]
- **Project basename**: Assumed `web_clickstream` as the main script and package basename. Rationale:
  descriptive; no external consumer pins a project name. [impact: low]
