Put JWT authentication back on the deployed API, configured for real Auth0 tokens.

Review feedback: the API is called from our own backend, not from a browser, so authentication costs nothing on the write path, while an unauthenticated endpoint lets anyone who learns the URL write junk into the pipeline. Two constraints came with it: it has to validate the Auth0 access tokens our backend already sends, and no sensitive values may be committed to this repository.

Auth0 signs access tokens with RS256, so the earlier HS256 shared-secret block could never have validated one. Per common-skills/configure-sqrl/vertx.md, asymmetric algorithms are supported and 'buffer' then holds the public key in PEM, and these configs support ${VARIABLE} substitution.

In web_clickstream-prod-package.json add the vertx block back with authKind JWT, a single pubSecKeys entry using algorithm RS256 and a buffer that reads from a variable rather than a literal, and jwtOptions whose issuer and audience also read from variables. Name the three variables clearly after this project so an operator can see what to set at deploy time, and document them in the README: what each one is, where its value comes from in Auth0, and that nothing secret is stored in the repository.

In web_clickstream-local-package.json restore the dummy HS256 block that the test runner's Authorization header already matches, so the write path tests exercise authentication the same way production will. Leave web_clickstream-test-package.json as it is.

Update the README authentication section to describe the two cases: the deployed API validates Auth0 RS256 tokens configured through those variables, while local and test use a dummy symmetric key. Re-run the tests and refresh only the snapshots this legitimately changes.
