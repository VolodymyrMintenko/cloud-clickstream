Scope every query to the caller's token instead of trusting its arguments.

Today JWT is authentication only: TopProjectsByUser, UserTrail and OrgTrail take userId and orgName as plain arguments, so any authenticated caller can read any other person's trail or any organization's. We want to expose these to the Cloud assistant as a tool, so the rows a caller sees must follow from their own token.

The access tokens are Auth0 tokens carrying these claims:
- sub, the standard subject claim, holding the same value we store in user_id (for example auth0|68dd...)
- https://datasqrl.com/data_group_ids, an array of strings with the organization ids the caller belongs to; these are the same ids we store in org_id
- https://datasqrl.com/global_admin, a boolean that is true for staff

The rule to enforce in the served queries:
- a caller whose global_admin claim is true sees every row, with no filtering
- everyone else sees a row when its org_id is in their data_group_ids claim, or when its user_id equals their sub claim, so a person always sees their own page views including the ones made outside any organization, where org_id is null
- the userId and orgName arguments stay as filters for narrowing a result the caller is already allowed to see, and stop being a way to reach anybody else's data

Note that these claim names contain slashes and colons, unlike the simple customerId and roles claims in the user_analytics template. Find out from the skill library how a namespaced claim is referenced in a SQRL query and use whatever that mechanism is; if it turns out a namespaced claim cannot be read, stop and say so in the run summary rather than inventing a workaround.

Update the API tests to cover three cases (an admin, a member of one organization, and somebody asking for an organization they do not belong to), extend the fixture data with a second organization if it needs one, update the README authentication section, and re-run the tests refreshing only the snapshots this legitimately changes.
